# 한국어 LLM 개발 상세 기획안

> 2026-09-17 구조 변경: 모델 아키텍처는 [v1 설계](architecture.md)를 우선한다. 이 문서의 50M 중심 일정·학습 토큰 예산은 과거 기획이며, 316M 본 학습 전에 실측 처리량과 자원에 맞춰 다시 산정한다.

작성일: 2026-09-14 · 상태: 구현 전 기획 · 대상: 프로젝트 소유자와 후속 구현 모델

## 1. 프로젝트 목표와 방향

**한국어 기본 언어 모델을 직접 사전학습하고, 같은 기본 모델에 분야별 어댑터를 붙여 적은 비용으로 특화할 수 있는 재현 가능한 실험 체계를 만든다.** 첫 특화 분야는 기존 README에 명시된 교통이다.

이 기획은 기존 `README.md`와 `docs/model-design.md`를 기반으로 한다. 기존 구조 설계는 유지하고, 실행 순서·데이터 계약·검증 기준·예산 통제·인수인계를 구체화한다. 문서의 수치 중 별도 출처가 없는 일정, 데이터량, 임계값, 하이퍼파라미터는 **프로젝트 제안값이며 실측 결과가 아니다.**

첫 결과물은 범용 상용 챗봇 수준의 모델이 아니다. 약 50M 규모의 모델로 사전학습부터 평가, 저장·재개, 분야 특화까지 완주하는 것이 1차 목표다. 한국어 이해와 대화 품질은 별도 평가에서 입증해야 한다.

### 최종 결과물

| 결과물 | 포함 내용 | 완료 증거 |
|---|---|---|
| 한국어 토크나이저 | BPE 모델, 특수 토큰, 정규화 정책, 학습 출처 | 독립 검증 문장 인코딩·디코딩 보고서 |
| 직접 학습한 Base 모델 | 구조 설정, 가중치, 추론 인터페이스 | 보류 데이터 평가와 고정 생성 예시 |
| 재현 가능한 학습 체계 | 데이터 버전, 설정, 재개 상태, 실험 로그 | 중단·재개 검증 기록 |
| 일반 지시 모델 | 한국어 SFT 결과 | 학습 전후 지시 수행 비교 |
| 교통 어댑터 | LoRA 가중치, 부모 모델 식별자 | 동일 모델 대비 분야 성능·일반 능력 비교 |
| 연구 보고서 | 성공·실패 실험, 비용, 한계 | 제3자가 읽고 재실행 가능한 기록 |

### 연구 질문

1. 정제한 한국어 데이터로 작은 모델의 보류 텍스트 예측 성능을 개선할 수 있는가?
2. 교통 분야 LoRA가 동일한 부모 모델보다 교통 작업 점수를 높이는가?
3. 특화 시 일반 한국어 능력 저하와 시간·메모리·저장 비용은 어느 정도인가?
4. 일반 데이터 혼합이 성능 저하를 줄이는가?

“한국어를 잘한다”는 표현은 한국어 문장 완성, 주어진 문서 이해, 요약, 지시 수행, 교통 입력 해석으로 나누어 검증한다.

## 2. 범위와 우선순위

| 우선순위 | 포함 항목 |
|---|---|
| P0: 반드시 완료 | 데이터 추적·분할, 토크나이저, 작은 모델 정합성, 50M 사전학습, 평가, 저장·재개 |
| P1: 프로젝트 목표 완성 | 일반 SFT, 교통 LoRA, 어댑터 호환성, 분야 개선·일반 능력 유지 평가 |
| P2: 자원에 따라 추가 | DAPT, Full FT 비교, QLoRA, DoRA, 100M 이상 확장, 시뮬레이션 연결 |
| 이후 별도 기획 | 1B 이상 대규모 학습, MoE, 멀티모달, RLHF, 상용 서비스 운영 |

교통 결과물의 첫 범위는 구조화된 교통 상황을 읽고 분석·설명하는 것이다. 실제 도로 신호 제어는 포함하지 않는다. 신호 정책 평가가 필요해지면 시뮬레이터에서 별도 실험하고, 설명 품질과 제어 성능을 구분한다.

### 직접 사전학습과 기존 모델 활용의 관계

| 경로 | 적합한 목적 | 이 프로젝트에서의 위치 |
|---|---|---|
| 처음부터 사전학습 | 모델 원리·데이터·학습 과정 연구 | 본 프로젝트의 기본 경로 |
| 공개 가중치 모델 미세조정 | 짧은 기간에 활용 가능한 특화 모델 확보 | 외부 비교 기준 또는 일정 부족 시 별도 대안 |
| 검색 결합 생성(RAG) | 갱신되는 문서를 근거로 답변 | 향후 응용; 직접 사전학습의 대체 성과로 계산하지 않음 |

대안으로 전환한다면 결과물의 출처를 명시한다. 기존 모델을 미세조정한 결과를 직접 사전학습한 모델이라고 기록하지 않는다.

## 3. 시작 전에 확정할 항목

아래 정보는 아직 확인되지 않았다. 기획은 진행할 수 있지만, 장시간 학습 전에 구현 담당자가 확인해야 한다.

| 항목 | 현재 기획상 가정 | 결정에 미치는 영향 |
|---|---|---|
| 목적 | 한국어 LLM 연구 및 교통 특화 실험 | 범용 제품보다 재현성·비교 실험 우선 |
| 인원 | 개인 또는 소규모 팀 | 순차 구현, 실험 수 제한 |
| 장비 | GPU 모델·VRAM 미확인 | batch, precision, 모델 확장 범위 |
| 비용 | 총액 미정 | 토큰 예산·실험 수·클라우드 이용 가능 여부 |
| 일정 | 8주 작업 예시 | GPU 처리량에 따라 학습 기간 재산정 |
| 데이터 | 확보량·사용 조건 미확인 | 목표 토큰량 달성 가능 여부 |
| 공개 범위 | 내부 실험 우선 가정 | 가중치·원문·어댑터 공개 조건 |

첫 의사결정 문서에는 GPU/VRAM, RAM, 여유 디스크, 주당 작업 시간, 전체 비용 상한, 완료 예정일, 사용 가능한 데이터 목록을 적는다. 예산을 모르는 상태에서 임의로 GPU를 구매하거나 유료 자원을 예약하지 않는다.

## 4. 첫 모델의 기술 사양

기존 `docs/model-design.md`의 기본값을 이어받는다.

| 항목 | 기본값 | 검증할 내용 |
|---|---|---|
| 구조 | Dense Decoder-only Transformer | 다음 토큰 예측 |
| Vocabulary | 총 32,000개 | 특수 토큰 포함 개수 고정 |
| Layer | 8 | 설정 기반 생성 |
| Hidden size | 512 | head 수로 나누어떨어짐 |
| Attention | MHA, 8 heads | head dimension 64 |
| Context length | 1,024 tokens | 초과 입력의 명시적 처리 |
| 위치 표현 | RoPE | 학습·추론 위치 계산 일치 |
| 정규화 | Pre-RMSNorm, 최종 RMSNorm | epsilon 등 세부 설정 기록 |
| FFN | SwiGLU, intermediate size 1,408 | projection 차원 일치 |
| Embedding / LM head | Weight tying | 저장·로드 후 공유 유지 |
| Bias / dropout | 없음 / 0.0 | 작은 데이터에서 과적합 점검 |

이 구성의 주요 가중치는 약 42.08M이다. 공유 임베딩 `32,000 × 512 = 16.384M`, attention은 layer당 `4 × 512² ≈ 1.049M`, FFN은 layer당 `3 × 512 × 1,408 ≈ 2.163M`이며 정규화 가중치를 추가한다. **50M은 단계 이름으로 사용하고, 실제 보고서에는 구현으로 집계한 정확한 파라미터 수를 기재한다.**

### 모델 확장 규칙

1. 초소형 디버그 모델: CPU 또는 작은 GPU에서 정합성 확인. 성능 비교 대상에서 제외한다.
2. 위 기본 모델: 정제 데이터와 BPE를 사용한 첫 사전학습 결과물.
3. 100M급 이상: 기본 모델의 학습·평가·재개가 검증되고 데이터와 GPU 예산이 충분한 경우에만 진입.

작은 모델의 학습률을 큰 모델에 최적값으로 그대로 적용하지 않는다. 각 규모에서 짧은 안정성 실험을 다시 한다. 처음에는 단일 장치 경로를 완성하고 분산 학습은 필요성이 확인된 뒤 추가한다.

## 5. 데이터 기획

### 5.1 데이터 종류와 예산

| 데이터 | 용도 | 초기 계획량 | 확장 조건 |
|---|---|---|---|
| 디버그 텍스트 | 학습 루프·암기 테스트 | 소수 문서 또는 수백~수천 토큰 | 자동 검증 통과 |
| 파일럿 사전학습 | 정제·처리량·loss 확인 | 1M~10M tokens | 보류 loss 개선·비용 추정 |
| 본 사전학습 | Base 모델 학습 | 100M tokens 중간 점검, 최대 1B 목표 | 중간 평가·데이터 가용성·예산 |
| 일반 한국어 SFT | 지시 수행 학습 | 검수된 2,000~10,000개 예시 | 품질 개선이 확인될 때 확대 |
| 교통 SFT | 분야 특화 | 검수된 1,000~5,000개 예시 | 동일 유형 중복보다 상황 다양성 우선 |
| 교통 DAPT | 분야 문체·용어 적응 | 별도 문서 확보 시 결정 | LoRA SFT 실패 원인 분석 후 |

토큰 수는 선택한 토크나이저로 측정한다. 고유 정제 토큰 수와 반복을 포함한 누적 학습 토큰 수를 별도로 보고한다. 100M 고유 토큰을 10번 반복했다고 1B 규모의 서로 다른 데이터를 확보한 것은 아니다.

1B는 비용 산정을 위한 목표이며 충분한 한국어 품질을 보장하는 숫자가 아니다. 모델 크기와 학습 토큰량을 함께 고려해야 한다는 근거는 [Chinchilla 논문](https://arxiv.org/abs/2203.15556)을 참고하되, 큰 모델에서 얻은 관계를 이 작은 모델의 품질 보증으로 사용하지 않는다.

### 5.2 출처 선정

우선 후보는 사용 조건이 명확한 한국어 백과·공공 문서·공개 교육 자료·직접 작성한 예시다. 뉴스·책·블로그·논문은 접근 가능하다는 이유만으로 수집 대상으로 확정하지 않는다. 데이터별 이용 조건, 학습 가능 범위, 재배포 조건을 확인한 뒤 포함한다.

혼합 비율의 첫 가설은 정제 후 학습 토큰 기준 한국어 일반 문서 80%, 영어·혼합 문서 10%, 수학·코드·구조화 텍스트 10%다. 소스 규모와 품질이 부족하면 비율을 억지로 맞추지 말고 실제 구성과 변경 이유를 기록한다. 교통 특화 데이터는 기본 사전학습과 분리해 특화 효과를 측정한다.

### 5.3 데이터 처리 순서

원본 등록 → 본문 추출 → 문자 정규화 → 언어·품질 검사 → 개인정보 처리 → 정확·근사 중복 그룹화 → 평가 오염 검사 → 문서 그룹 단위 분할 → 학습 split으로 토크나이저 학습 → 토큰화 → shard 생성 → manifest 고정.

| 처리 | 요구사항 |
|---|---|
| 정규화 | Unicode NFC를 기본안으로 사용하고 한글·수식·코드 훼손 여부 확인 |
| 품질 필터 | 빈 본문, 인코딩 오류, 과도한 반복, 광고·메뉴 위주 문서 제거 |
| 중복 제거 | exact hash와 근사 중복 사용; 연결된 문서·복제본은 같은 split |
| 개인정보 | 연락처·식별정보 등 불필요한 개인정보 제거; 처리 수량 기록 |
| 평가 오염 | 정답·문제·근사 복제본이 학습에 들어가지 않도록 검사 |
| 분할 | train/validation/test를 문서 그룹 기준 약 98/1/1로 시작 |
| 품질 표본 | 출처별 최소 100개 또는 전체가 더 작으면 전수 검수 |
| 재현성 | 처리 버전, seed, 입력·출력 hash, 탈락 사유별 수량 기록 |

청크를 먼저 만든 뒤 무작위로 나누면 같은 원문이 학습과 평가에 동시에 들어갈 수 있다. 문서 계보와 중복 그룹을 먼저 고정한다. 시간 변화가 중요한 교통 데이터는 시간·교차로·시뮬레이션 시나리오 그룹을 기준으로 별도 보류한다.

### 5.4 필수 데이터 필드

원문 레코드: `document_id`, `source_id`, `source_uri`, `license_id`, `collected_at`, `text`, `language`, `content_hash`, `group_id`, `split`, `processing_version`.

SFT 레코드: `sample_id`, `messages`, `task_type`, `source_document_ids`, `group_id`, `split`, `review_status`, `data_version`. messages는 role과 content를 가진 순서 있는 대화다. 합성 예시는 생성 모델·버전·생성 조건·검수 상태를 추가 기록한다. 평가 문제와 같은 템플릿을 단어만 바꾸어 대량 생성하지 않는다.

Manifest: 소스별 문서 수, 언어·작업별 분포, 고유 토큰 수, shard 목록·hash, 토크나이저 hash, split별 크기, 제외 이유를 포함한다.

## 6. 토크나이저 기획

BPE 16K, 32K, 48K를 동일한 학습 표본으로 비교한다. 최종 선택 기본안은 기존 설계의 32K다. 특수 토큰과 정규화 정책은 본 사전학습 전에 고정한다.

| 평가 항목 | 방법 |
|---|---|
| 한국어 압축 효율 | 독립 문장 집합의 문자당 token 수, 길이 분포 |
| 혼합 입력 | 영어, 숫자, 단위, 코드, 교통 용어 포함 |
| 복원 | 정규화된 원문 기준 decode(encode(text)) 일치 |
| 미지원 문자 | byte fallback 등 정책과 손실 여부 확인 |
| 긴 문서 | 1,024 tokens 안에 담기는 본문량과 잘림 비율 |
| 비용 | vocabulary 증가로 늘어나는 임베딩·logits 비용 |

필수 특수 토큰은 PAD, BOS, EOS 및 대화 역할 구분자다. 실제 토큰 문자열·ID·EOS 삽입 규칙을 버전으로 저장한다. PAD의 loss mask는 token ID만으로 추측하지 않고 실제 패딩 위치를 기준으로 적용한다.

토크나이저를 바꾼 모델의 perplexity를 직접 비교하지 않는다. 토크나이저 간에는 정규화된 동일 텍스트에 대한 byte당 NLL 등 공통 단위를 쓰거나 실제 작업 점수로 비교한다. Character tokenizer는 디버그 전용이며 최종 토크나이저와 성능 실험 계열을 분리한다.

## 7. 학습 단계와 완료 기준

### 단계 A: 정합성 확인

구현 담당자가 먼저 증명할 항목이다.

- 입력 `tokens[0:T]`의 정답은 `tokens[1:T+1]`이며 shift는 한 번만 수행한다.
- 미래 위치의 토큰을 바꾸어도 이전 위치 logits가 변하지 않는다.
- padding 위치는 loss 집계에서 제외된다.
- 작은 표본을 반복 학습하면 초기보다 loss가 크게 감소한다.
- gradient가 유한하고 의도한 가중치에 도달한다.
- eval 모드 저장·재로드의 logits가 설정된 수치 오차 범위에서 일치한다.
- 고정 seed·고정 데이터의 짧은 재개 실험이 연속 실행과 일치하거나, 비결정성의 허용 오차와 원인을 기록한다.

GPU가 없는 경우에도 이 단계의 작은 CPU 테스트는 진행할 수 있다. 이 단계 실패 시 모델 확대나 본 학습을 시작하지 않는다.

### 단계 B: 파일럿 사전학습

| 항목 | 제안 시작값 |
|---|---|
| Optimizer | AdamW, betas 0.9/0.95 |
| Peak learning rate | 3e-4 |
| Weight decay | 0.1, bias·norm 등 제외 정책 명시 |
| Precision | 지원 장치에서 BF16; FP32 기준 경로 유지 |
| Scheduler | warmup 후 cosine, 최종 LR 비율 0.1 제안 |
| Warmup | 예정 optimizer step의 1%, 최소 1 step |
| Gradient clipping | global norm 1.0 |
| Context | 1,024 |
| 유효 batch | optimizer step당 약 32,768 tokens로 시작 |

유효 batch tokens = micro batch × context length × gradient accumulation × 장치 수다. 패딩이 있으면 실제 유효 토큰도 별도로 집계한다. VRAM에 따라 micro batch를 줄이고 accumulation으로 맞춘다. BF16 미지원 환경의 FP16 경로는 별도 수치 안정성 검증이 필요하다.

위 설정은 기존 설계를 기반으로 한 출발점이다. 첫 파일럿에서 학습률 1e-4, 3e-4 두 개만 같은 데이터·토큰 예산으로 비교한다. train loss 하락만으로 통과하지 않고 보류 loss, 반복 생성, 처리량, 메모리를 함께 본다.

### 단계 C: 본 사전학습

100M tokens에서 첫 중간 점검을 하고, 데이터·비용·보류 성능이 적절하면 누적 1B 목표까지 진행한다. scheduler의 총 길이는 실행 시작 전에 명시한다. 100M 완주 run을 1B로 늘릴 때는 새 schedule 계획을 가진 분기 run으로 기록하고 같은 실험의 단순 재개처럼 취급하지 않는다.

평가·체크포인트 간격은 첫 처리량 측정 후 설정한다. 시작안은 10M 학습 토큰마다 평가, 최대 30분 분량의 작업을 잃지 않는 저장 주기다. latest·best·주요 milestone을 보존하고 보관 상한을 둔다. 저장 공간 부족 시 조용히 저장을 건너뛰지 않는다.

정지 조건: 비유한 loss/gradient, 반복되는 OOM, 데이터 hash 불일치, 비용 상한 도달, 연속 3회 보류 loss 악화. 성능 악화는 자동 폐기 대신 데이터·학습률·과적합을 진단한 뒤 재개 여부를 정한다.

### 단계 D: 일반 한국어 SFT

Base는 문장을 이어 쓰도록 학습한 모델이므로 곧바로 대화 모델이라고 판단하지 않는다. 일반 SFT로 질문·요약·정보 추출·출력 형식 지시를 학습한다. 50M급에서는 Full FT를 기본 시작안으로 하고 1e-5~5e-5 범위의 짧은 실험으로 확인한다. 1 epoch부터 평가하며 횟수 증가를 자동 성능 개선으로 가정하지 않는다.

대화 템플릿을 고정하고 assistant 답변 토큰에만 loss를 적용하는 정책을 기본으로 한다. 시스템·사용자·패딩 마스킹과 EOS 학습이 의도대로 되는지 예시 단위로 검증한다. TRL은 대화형 데이터와 assistant-only loss를 지원하지만 템플릿 조건이 있으므로 후속 구현에서 호환성을 확인한다. [TRL SFT 문서](https://huggingface.co/docs/trl/sft_trainer)

### 단계 E: 교통 LoRA

일반 SFT 모델을 부모로 고정한 뒤 교통 LoRA를 적용한다. rank 16, alpha 32, dropout 0.05, attention의 Q/V projection을 첫 제안값으로 사용한다. 학습률은 1e-4로 짧게 시작하고 validation으로 조정한다. 성능 부족 시 rank 8/32 또는 Q/K/V/O·FFN 대상 확대를 한 번에 하나씩 비교한다.

작은 모델은 기반 능력이 부족해 LoRA만으로 원하는 결과를 못 낼 수 있다. 이 경우 데이터·기반 능력·업데이트 용량을 구분해 진단한다. LoRA가 부모 가중치를 고정해도 어댑터를 켠 출력의 일반 능력은 나빠질 수 있으므로 반드시 측정한다.

QLoRA는 실제 메모리 절감 필요가 확인된 경우 비교한다. 양자화와 LoRA 결합에는 지원 모듈·장치·라이브러리 호환성이 필요하며, 직접 작성한 모델에 자동 적용된다고 가정하지 않는다. [PEFT 양자화 문서](https://huggingface.co/docs/peft/developer_guides/quantization)

DAPT는 분야 문서의 다음 토큰 예측, SFT는 지시와 답변 학습, LoRA는 가중치 업데이트 방식이다. 서로 같은 분류가 아니다. DAPT가 부모 가중치를 바꾸면 새 부모 ID를 발급하고 이후 어댑터를 다시 연결한다.

## 8. 교통 특화 작업 명세

### 입력

첫 단계는 영상 입력 없이 텍스트·구조화 수치를 받는다. 필드는 관측 시각, 교차로 ID, 방향·차로별 대기 차량 수, 유입량, 관측 구간, 평균 대기 시간, 현재 신호 상태, 누락 여부다. 각 수치에 단위를 명시하고 음수·결측·비현실적 범위를 검증한다.

### 출력

상황 요약, 입력 수치에 근거한 혼잡 방향, 추가 확인이 필요한 정보, 분석의 제한점을 반환한다. 구조화 출력이 필요하면 `summary`, `observations`, `missing_fields`, `insufficient_data` 필드를 사용한다. 우선순위는 제공된 정책·정답 기준 안에서만 제안한다.

예: “북쪽 대기 30대, 동쪽 대기 8대”에는 북쪽 대기가 더 많다고 설명할 수 있다. 차로 수·회전 교통량·보행자·신호 제약이 없으면 최적 녹색 시간을 확정하지 않는다. 정확한 합계·비율 계산은 기준 계산기로 검증하고, 모델의 문장 유창성을 수치 정확성과 혼동하지 않는다.

### 데이터 유형

정상 혼잡, 방향별 불균형, 비혼잡, 결측, 상충 센서, 단위 차이, 시간 변화, 판단 불가 사례를 포함한다. 특정 방향이 정답인 예시만 과도하게 넣지 않는다. 합성 데이터는 시나리오 그룹별로 분리해 같은 생성 규칙의 거의 동일한 예시가 test에 섞이지 않게 한다.

시뮬레이션을 확장할 경우 고정 시간 제어와 사전 정의한 규칙을 기준선으로 두고 동일 수요·시드에서 평균 대기 시간, 큐 길이, 통과량을 비교한다. LLM의 설명 점수만으로 신호 제어 개선을 주장하지 않는다.

## 9. 평가 설계와 성공 기준

### 9.1 평가 묶음

| 묶음 | 제안 규모 | 주요 지표 |
|---|---|---|
| 보류 일반 텍스트 | 출처별 충분한 문서, 전체 약 1%부터 | token-weighted NLL, 동일 tokenizer의 PPL |
| 일반 한국어 작업 | 개발 150개 + 봉인 test 300개 | 문서 QA, 요약, 추출, 지시 준수 |
| 교통 작업 | 개발 150개 + 봉인 test 300개 | 수치 일치, 해석, 형식, 판단 유보 |
| 고정 생성 회귀 | 대표 프롬프트 50개 | 반복, 문장 붕괴, 길이·종료 문제 |
| 성능 측정 | 고정 입력·출력 길이, 반복 측정 | tokens/s, 지연 p50/p95, peak VRAM |

수백 개 평가는 초기 프로젝트용이며 큰 모집단에 대한 품질 보증이 아니다. test는 하이퍼파라미터 선택에 사용하지 않는다. 봉인 test 결과를 보고 수정하면 다음 최종 평가는 새 test 버전을 만든다.

### 9.2 채점 정책

정답이 있는 작업은 exact match·수치 오차·필드 유효성으로 자동 채점한다. 서술형은 사실 일치 0~2, 핵심 포함 0~2, 지시 준수 0~1의 5점 rubric을 사용한다. 일반 작업과 교통 작업 내부의 유형별 macro average를 계산해 특정 유형의 문항 수가 전체 점수를 지배하지 않도록 한다.

사람 평가자는 모델 이름을 가린 응답을 검토한다. 최소 20%를 두 사람이 중복 평가하고 불일치를 조정한다. 모델 자동 심사는 보조로 사용하고 평가 모델·프롬프트·순서 편향을 기록한다. [Hugging Face 평가 가이드](https://github.com/huggingface/evaluation-guidebook)

### 9.3 제안 통과 기준

| 대상 | 초기 통과 기준 |
|---|---|
| 정합성 | causal mask, loss mask, gradient, 저장·재개 필수 검증 통과 |
| Base 학습 | 동일 보류 집합 NLL이 무학습 초기 모델 대비 10% 이상 감소 |
| Base 품질 해석 | 위 기준은 학습 작동 확인; 실제 유용성은 작업 평가로 별도 판단 |
| 일반 SFT | 일반 작업 점수가 Base보다 개선되고 응답 붕괴가 증가하지 않음 |
| 교통 특화 | 같은 부모 대비 교통 점수 +10 percentage points 목표 |
| 일반 능력 유지 | 부모 대비 일반 작업 점수 하락 5 percentage points 이내 목표 |
| 형식 준수 | 구조화 응답이 필요한 test의 95% 이상 schema 통과 |
| 재현성 | 동일 산출물 재로드 시 평가 재현; 실행 환경 차이 명시 |

성능 임계값은 첫 기준선 평가 후 개발셋에 근거해 한 번 검토하고 test를 열기 전에 확정한다. 표본 불확실성을 paired bootstrap 등의 95% 구간으로 함께 보고한다. 효과가 불분명하면 “개선 입증 실패”로 기록하며 보기 좋은 예시만으로 성공 처리하지 않는다.

## 10. 실험 계획

실험을 모든 조합으로 늘리지 않는다. 먼저 기준선을 만들고 한 변수씩 바꾼다.

| ID | 질문 | 변경 항목 | 진행 조건 |
|---|---|---|---|
| EXP-001 | 전체 경로가 맞는가? | 초소형 모델 정합성 | 최초 필수 |
| EXP-002 | 토크나이저 선택이 적절한가? | BPE 16K/32K/48K | 정제 train 표본 확보 |
| EXP-003 | 학습률이 안정적인가? | 1e-4 vs 3e-4 | 같은 파일럿 토큰 예산 |
| EXP-004 | 기본 모델이 학습되는가? | 선택 구성 본 학습 | 비용·품질 gate 통과 |
| EXP-005 | 지시 학습 효과가 있는가? | Base vs 일반 SFT | Base 평가 완료 |
| EXP-006 | 교통 LoRA가 개선하는가? | 일반 SFT 부모 vs 교통 LoRA | 교통 개발셋 고정 |
| EXP-007 | 일반 능력을 유지할 수 있는가? | 교통/일반 100/0 vs 90/10 | 특화 효과 확인 |
| EXP-008 | 업데이트 방식의 차이는? | Full FT vs LoRA | 추가 자원 확보 |
| EXP-009 | 추가 효율화가 필요한가? | QLoRA 또는 DoRA | 명확한 비교 목적 |

혼합 비율은 loss가 적용되는 유효 토큰 기준으로 정의하고 예시 수 비율도 보조 기록한다. 주요 결론 실험은 가능하면 3 seeds로 반복한다. 비용이 부족해 1회만 수행했다면 그 한계를 보고한다.

Full FT와 LoRA는 동일한 부모·데이터·평가·토큰 예산을 공유하되 각 방식의 학습률은 동일한 탐색 예산 안에서 조정한다. 같은 학습률을 강제하는 것이 공정한 비교는 아니다. QLoRA는 양자화된 부모만의 기준선도 측정하여 양자화 손실과 특화 효과를 구분한다.

## 11. 자원과 비용 산정

현재 GPU와 요금이 확인되지 않아 고정 금액이나 완료 시간을 약속하지 않는다. 구매 후보를 결정하기 전에 실제 구현의 처리량을 측정한다.

### 산정식

- 순수 학습 시간(초) = 예정 누적 토큰 / 실측 전체 장치 합산 tokens/s.
- 예상 실행 시간 = 순수 학습 시간 × 평가·저장·재시도 여유 계수.
- GPU 비용 = GPU당 시간 요금 × 장치 수 × 실행 시간(시간).
- 총비용 = GPU + 저장 + 전송 + 데이터 준비·검수 비용.

예를 들어 **가상의** 처리량 10,000 tokens/s라면 1B tokens는 순수 학습 약 27.8시간이고 여유 30% 적용 시 약 36.1시간이다. 1,000 tokens/s라면 약 361시간이다. 이 예시는 실제 장치 성능이나 시장 요금이 아니다.

워밍업 후 최소 수백 step에서 data loading·backward·optimizer를 포함한 처리량을 측정한다. 평가와 저장 비용은 별도 측정한다. 추론 tokens/s를 학습 속도로 사용하지 않는다.

### 메모리와 저장

Mixed precision Adam 학습 상태는 구성에 따라 대략 parameter당 12~20 bytes 수준의 계획용 범위를 사용할 수 있다. 약 42M이면 약 0.5~0.84GB지만 이는 가중치·gradient·optimizer 등의 거친 추정일 뿐이다. activation, logits, attention, kernel buffer, allocator가 추가되므로 필요한 VRAM 전체를 의미하지 않는다. 실제 peak allocated/reserved 메모리로 판단한다.

1B token ID를 uint16으로 저장하면 약 2GB, uint32라면 약 4GB다. 이것은 토큰 배열만의 용량이며 원본·정제본·메타데이터·복사본·체크포인트는 추가다. vocab과 특수 ID 범위에 맞는 dtype을 선택한다.

예산 배분 시작안: 파일럿·디버그 15%, 본 사전학습 45%, SFT·어댑터 20%, 평가·재실험 여유 20%. 상한 70% 사용 시 잔여 실험을 재산정하고 90%에서는 새 대규모 실험을 열지 않는다. 예산을 줄일 때 평가·재현성보다 모델 크기·토큰량·실험 가짓수를 먼저 줄인다.

## 12. 모듈 경계와 산출물 계약

아래 경로는 후속 구현의 예정 위치이며 이번 작업에서는 구현 파일을 생성하지 않는다.

| 위치 | 책임 | 입력 → 출력 |
|---|---|---|
| datasets/ | 수집·정제·분할·토큰 shard | 승인된 원문 → manifest와 shards |
| tokenizer/ | 토크나이저 학습·검증 | train 표본 → tokenizer와 report |
| model/ | 설정 기반 Transformer | token IDs·mask → logits, 선택적 loss |
| training/ | pretrain·SFT·resume | config·manifest → checkpoint·로그 |
| adapters/ | LoRA 적용·저장·해제 | 정확한 부모 checkpoint → adapter |
| evaluation/ | 고정 평가·성능 측정 | checkpoint·평가 버전 → 결과·응답 |
| configs/ | 모델·데이터·학습 설정 | 명시적 설정; 시작 시 검증 |
| experiments/ | 실험 기록·비교 | 실행 ID → 설정·지표·결론 |
| checkpoints/ | 대용량 가중치 | Git에 올리지 않는 학습 산출물 |

### 체크포인트에 포함할 상태

모델 가중치, optimizer, scheduler, step, 누적 토큰 수, RNG states, sampler 순서와 cursor, 필요 시 scaler, config, 데이터 manifest hash, tokenizer hash, 코드 revision, 환경·패키지 버전이다. 재개 시 불일치를 검증한다. 가중치만 불러오는 것은 완전한 학습 재개와 구분한다.

### 어댑터 호환성

base checkpoint hash, tokenizer hash, target module 목록, rank/alpha/dropout, 학습 데이터·설정, 생성 시각을 기록한다. 다른 부모에는 묵시적으로 로드하지 않는다. adapter off는 부모 출력과 일치해야 하며 merge 결과도 허용 수치 오차 안에서 확인한다. QLoRA merge·export는 별도 호환성 검증 대상으로 둔다.

### 추론 요구사항

처음에는 단일 입력 배치의 로컬 CLI 수준으로 충분하다. seed, temperature, top-p, max_new_tokens를 명시하고 greedy 모드도 제공한다. context 초과, 빈 입력, EOS 종료, 잘못된 adapter 조합을 분명하게 처리한다. API·웹 UI는 모델 검증 후 추가한다.

직접 구현 모델을 TRL/PEFT 같은 도구에 연결하려면 모델 설정·forward·저장 포맷·target module 호환 계층이 필요할 수 있다. 기본 사전학습은 직접 관리하는 학습 루프로 시작하고, 라이브러리 연결은 작은 smoke test를 통과한 뒤 채택한다. 라이브러리 버전은 구현 시 호환성을 확인해 고정한다.

## 13. 8주 작업 예시

아래는 개인 또는 소규모 팀의 작업 순서 예시다. 데이터 접근 지연과 GPU 학습 시간은 첫 실측 후 반영한다.

| 기간 | 작업 | 완료 조건 |
|---|---|---|
| 1주 | 환경·비용 확정, 소스 등록, 평가 rubric·데이터 계약 | 사용 가능한 데이터와 자원 목록 |
| 2주 | 정제·분할, 토크나이저 비교, 초소형 정합성 | 데이터 보고서·필수 검증 통과 |
| 3주 | 50M급 파일럿·처리량·재개 테스트 | 본 학습 예상 시간·비용 산출 |
| 4~5주 | 본 사전학습과 중간 평가 | Base checkpoint·보류 평가 |
| 6주 | 일반 SFT·교통 데이터 검수 | 일반 지시 기준선 |
| 7주 | 교통 LoRA·혼합 비율 비교 | 분야 개선·일반 능력 비교 |
| 8주 | 봉인 test, 재현성·보고서, 데모 | 모델 카드·실험 결론·인수인계 |

일정 초과 시 100M 이상 확장, DoRA, QLoRA, DAPT를 뒤로 미룬다. 본 학습을 감당할 수 없으면 더 작은 토큰 예산으로 완주하고 성능 한계를 기록한다. 서비스 품질이 더 중요해지는 경우 공개 모델 미세조정으로 경로 변경을 명시한다.

## 14. 주요 위험과 대응

| 관측되는 문제 | 먼저 확인할 것 | 대응 |
|---|---|---|
| loss가 줄지 않음 | label shift, mask, optimizer 연결 | 초소형 암기 테스트로 복귀 |
| train만 개선됨 | 중복·반복 노출·데이터 규모 | 정제·검증 분리 확인, 조기 종료 |
| 문장은 생성하지만 지시 무시 | Base와 SFT 단계 차이 | 일반 SFT 적용·템플릿 점검 |
| 교통 용어만 암기 | 데이터 다양성·시나리오 누출 | 미관측 시나리오 평가·예시 개선 |
| 특화 후 일반 능력 저하 | 혼합 비율·LR·학습량 | 일반 데이터 혼합, 학습량 축소 |
| 작은 모델 품질 한계 | clean test와 외부 기준선 | 규모 확대 또는 적용 범위 축소 |
| 재개 후 결과 급변 | RNG·sampler·scheduler 상태 | 복구 계약 수정 후 재검증 |
| GPU 메모리 부족 | 실제 peak와 sequence 비용 | micro batch 축소, accumulation 등 검증 |
| 어댑터 적용 실패 | 모듈명·부모 hash·라이브러리 지원 | 최소 호환 실험 후 연결 |
| 평가 점수만 비정상적으로 높음 | 원문·문제·템플릿 중복 | 오염 제거, 새 test 구성 |

## 15. 구현 담당 모델에게 전달할 지시문

> 이 저장소의 README.md, docs/model-design.md, docs/project-plan.md를 읽고 구현한다. 기획 수치를 실측값으로 취급하지 않는다. 기존 변경 내용을 보존하고, 먼저 실제 환경과 데이터 가용성을 조사한다. 처음에는 데이터 계약, 초소형 모델, 정합성 테스트, 저장·재개 경로를 구현한다. 장시간 학습은 처리량·메모리·토큰 예산·비용 상한이 확인된 뒤 진행한다. 단계별 완료 증거를 experiments/에 남긴다. Base 사전학습, 일반 SFT, 교통 LoRA를 구분하고 정확한 부모 checkpoint와 tokenizer를 연결한다. 봉인 test를 설정 선택에 사용하지 않는다. 구현되지 않은 기능, 실행하지 않은 학습, 측정하지 않은 성능을 완료했다고 보고하지 않는다. 초기 범위는 P0이며 P1으로 순차 확장한다. P2 기능은 필요성이 입증될 때만 추가한다.

## 16. 지금 무엇부터 해야 하는가

첫째, GPU·비용·기간을 기록한다. 둘째, 사용 가능한 한국어 문서를 작은 표본으로 확보하고 출처·사용 조건을 정리한다. 셋째, “무엇을 잘하면 성공인가”를 보여주는 일반 질문 30개와 교통 질문 30개를 먼저 작성해 rubric을 검토한다. 이 초기 문항은 개발용으로 사용하고 최종 test와 분리한다. 넷째, 구현 담당 모델에 위 지시문을 전달해 초소형 모델의 학습·평가·저장·재개부터 완성하게 한다.

**첫 주의 성공은 큰 모델을 학습시키는 것이 아니라, 학습할 데이터·사용할 자원·평가할 질문·검증 순서를 확정하는 것이다.**
